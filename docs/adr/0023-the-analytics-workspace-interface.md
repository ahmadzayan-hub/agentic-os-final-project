# ADR 0023 — The analytics workspace interface

**Status:** Accepted
**Date:** 2026-10-16
**Plan:** `docs/UI_PLAN.md`
**Keeps:** WCAG 2.2 AA in both languages (ADR 0018), no third-party requests, no UI or chart library

## Context

The interface was built for a chat and a single run view. The direction set in `project-progress.md` is an analytics workspace: several datasets, analyses, dashboards and live data. That needs a place to start (an overview), a place for data (datasets), and a visual system dense enough for dashboards.

The user asked for the UI to be planned and built with the `ui-ux-pro-max` skill. It is a third-party skill: local search over curated style, palette, typography, UX and chart guidance.

## Decision

1. **The skill is vendored** in `.claude/skills/ui-ux-pro-max/`, pinned to commit `56ea9cf` with its MIT licence. It was reviewed as code: standard library only, no network access, and it writes files only when asked to save (see its `PROVENANCE.md`). Its output is advice. Where it conflicts with this repository's rules, the rules win.
2. **The design system comes from the skill.** It was generated with an enterprise analytics dashboard query (variance 3, motion 3, density 8) and persisted in `design-system/agentic-os/MASTER.md`. An *Agentic OS decisions* section overrides the generated values in four places:
    - amber is the highlight, not the primary action;
    - control borders are darkened to 3:1, where the generated `#DBEAFE` was about 1.2:1;
    - motion is CSS only, where the recommendation used GSAP;
    - Arabic keeps a system stack, because Fira has no Arabic letters.
3. **Fonts are bundled, not fetched.** Fira Sans and Fira Code come from `@fontsource` (OFL-1.1, Latin subsets only), built into `/assets` and cached by the service worker. The app still works offline and makes no third-party request. These are the first runtime dependencies beyond React, and they are font files, not code.
4. **The navigation grows by addition.** Overview and Datasets join the existing views. Labels the tests and users rely on stay as they are until dashboards (phase 3) give "Analyses" a reason to replace "Runs".
    - The sidebar groups the views: *Analyse* (Overview, Datasets, Runs), *Work with* (Workspace, Memory, Activity), then Preferences.
    - A phone's bottom bar holds five places: Overview, Datasets, Runs, Workspace and *More*, which opens the drawer with the rest. Focus returns to whichever control opened the drawer.
    - The session still opens on the assistant, which greets a newcomer. The Overview is one click away.
5. **A stored dataset is analysed by reference.** Choosing *Analyse* on a stored dataset sends its id (`dataset_id`, which `POST /api/runs` already accepted), never its contents again. The run form then shows the chosen dataset in place of the sample and upload switch.
6. **The Overview shows only what the server said.** Its figures are counts over `GET /api/runs` (at most 50, and the view says so when the list is full) and `GET /api/usage`. The latest findings are the headlines of the most recently updated run that has reports. They keep their report's language (ADR 0022), and the run's state is shown beside them, so nothing reads as approved that was not.
7. **Charts stay hand-drawn SVG.** Negative bars are drawn from a zero line, and forecasts are marked as such. Each later chart type follows the plan's chart table.

## Consequences

- The palette changes from indigo to navy and blue, and the brand mark loses its gradient. Every text pairing was rechecked: 4.5:1 or better in both themes, and 3:1 or better for control borders.
- The JavaScript budget rises from 90 KB to 100 KB gzipped, to leave room for phases 2 and 3; phase 1 builds to 92 KB. The five WOFF2 font files add about 119 KB, cached after the first visit.
- The screenshots in `docs/screenshots/` are regenerated by the end-to-end screenshot spec, with reduced motion so that no capture catches a colour mid-transition. They are real captures, not mock-ups.
- Phases 2 to 6 need backend milestones A1 to A7. The dataset API's decision record becomes ADR 0024.

## Verified (phases 0 and 1, 2026-10-16)

- 52 frontend unit tests, including the Overview's counting rules, its empty, loaded and error states, and a stored dataset analysed by id.
- 60 end-to-end checks across desktop and phone: 57 run and pass, and 3 are skipped by design because each covers one viewport only. Axe reports no WCAG 2.2 AA violation on the Overview, the Datasets view or the run form with a stored dataset, in English or Arabic. Neither view scrolls sideways at 320 px in either language.

## What would prove this wrong

- A Lighthouse accessibility score below 100, or any axe violation, in either language or theme.
- Performance below 95, or the fonts causing visible layout shift (CLS 0.1 or more).
- Users finding Overview slower to reach their work than the chat was. If that happens, the session should open on the view last used.

## Amendment, 2026-10-16: serving the build as Vercel does

**Found.** A Lighthouse audit of the self-hosted server (`python scripts/serve.py`, mobile emulation, Lighthouse 13.4.1, three runs) scored Performance 86, 87 and 88, under the 95 this record sets. Accessibility, Best Practices and SEO were 100. The largest contentful paint took 3.4 s. The cause was the server, not the interface. It sent the 323 KB script and the 38 KB stylesheet uncompressed, and with no cache headers. Vercel's CDN compresses both, and `vercel.json` marks `/assets/` as immutable, so production and a self-hosted copy behaved differently.

**Decided.** The FastAPI server now serves the build the way `vercel.json` does:

- Responses outside `/api/` are gzip-compressed when the browser accepts it and they are over 1 KB.
- API responses are never compressed. A response can carry a token beside text the caller chose, which is the shape a compression side channel (BREACH) needs, and the bodies are small JSON anyway.
- `/assets/` files are sent with `Cache-Control: public, max-age=31536000, immutable`, because Vite names each one by its content hash.
- The page, the service worker and the manifest are sent with `no-cache`, so a new build is picked up on the next visit.
- API responses keep `no-store`.
- An `/api/` path that no route matches now returns 404. Before this change, it returned the interface's page.

**Measured after,** with the same tool and settings:

| Run | Performance | Accessibility, Best Practices, SEO | LCP | CLS | TBT |
| --- | --- | --- | --- | --- | --- |
| Mobile (each of 3 runs) | 99 | 100 | 2.0 s | 0 | 0 to 10 ms |
| Desktop (1 run) | 100 | 100 | 0.5 s | 0 | 0 ms |

The page now transfers 151 KB. Six tests in `tests/test_api.py` cover this, using a stand-in build so that they run in CI, where the Python tests run before the frontend build.

**Still open.** Lighthouse estimates 43 KB of the script is unused on the first view. Splitting views into chunks loaded on demand would recover it. That belongs with phase 2, when the views grow.
