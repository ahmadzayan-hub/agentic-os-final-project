## Product rationale

The workspace should answer three questions: What did the agents do? What supports this finding? What needs my decision? A stable shell holds context; findings lead into evidence and a specific report. Amber draws attention to a pending human decision. Blue identifies the next useful action. Completion, passed checks, approval and publication remain separate concepts.

The current source takes precedence over the older brief. Ingestion already supports CSV/TSV, XLSX, JSON and JSON Lines, previews and saved column mappings (ADRs 0024–0025). Actual limits are 4 MB uploaded, 10 MB after canonical CSV conversion, and 50,000 rows. Sheet names are returned; choosing another workbook sheet still needs an API. Do not label these implemented formats or mapping as future concepts.

## Navigation and primary journey

Desktop: approximately 240 px sidebar; Overview, Datasets, Runs, Approvals, Workspace, Memory, Activity and Preferences. Phones: Overview, Datasets, Runs, Workspace and More. More exposes the other destinations. Keep the current labels; “Analyses” and Dashboards belong to their planned phase.

Addresses are `#/overview`, `#/datasets`, `#/runs`, `#/runs/{id}`, `#/approvals`, `#/assistant`, `#/memory`, `#/activity` and `#/preferences`. Browser back and reload restore the destination. Skip links move focus without changing these hashes.

1. **Try sample data:** Overview opens the existing run form with sample selected. Review the goal, report language and four-band plan; no analysis begins merely by selecting data.
2. **Start:** submit once. Display only the run returned by the backend. The URL acquires its stable identifier.
3. **Follow:** show goal, dataset, report language and observed state. Pause/resume/cancel operate through the existing endpoints. Explain that the default execution depends on keeping Runs open.
4. **Inspect:** show the first finding in the header, four main perspective cards, and the separate Experiment report. “Why is this true?” opens the relevant stage's claims, references, precise checks and report calculations.
5. **Review:** display the exact report and publication metadata in ApprovalCard. The full report is available through an expandable, bounded, keyboard-scrollable preview. A missing report disables publishing.
6. **Approve or reject:** lock the decision while awaiting the server. A failure triggers a state read; it never automatically repeats publication. A changed artifact requires a valid new server approval.
7. **Published:** show success only when `report.published_path` is returned. Display that path and make “Read the published report” the primary action; it focuses the exact returned report. Reopen the run from its link for later review. The server filesystem path is text, not an invented web URL.

Report text and arbitrary tool results are React text, never injected HTML or executable UI. A future structured payload must be versioned and limited to a registered catalog. Unknown versions/components use a readable text fallback and keep evidence links only when an actual valid identifier is supplied. No new library or runtime protocol is required for these current components.

## State, continuity and assurance

| Situation | Visible behavior and recovery |
| --- | --- |
| Navigate away | React Activity preserves view state and stops hidden effects. This tab stops scheduling advance calls. A submitted request can finish; a configured worker or another tab can continue. |
| Refresh or reopen | Restore the server session and hash address; fetch current run. Composer and question text restore from this tab's sessionStorage. Pasted CSV and selected File objects require selection again; raw data is not persisted as a draft. |
| Backend disconnect | Retain the last in-memory snapshot, indicate connection/error and last observation time where available, offer read recovery. A cold offline launch has the cached shell but cannot fetch private reports. The service worker never caches API data. |
| Same run in another tab | Each tab reads server snapshots; the server serializes/leases actual execution. An approval may already be decided or invalidated elsewhere. Reconcile using GET; never assume this tab is authoritative. |
| Uncertain POST response | Keep the refusal visible and read the current run. Do not replay a publication, cancel or start request automatically. A server idempotency key for run creation is a separate API proposal; avoid blindly pressing Start again. |
| Stage finished | Only that stage's execution finished; this does not certify all calculations. |
| Validation checks passed | Only the named returned checks passed; expose their detail. No general “Verified” product badge. |
| Human approval required | A pending approval blocks the publishing task. |
| Approval recorded | The server accepted the decision; publication can still fail. |
| Publication succeeded | The server returned the publication path for this report. |

## Visual, responsive and accessibility specifications

Use `tokens.css` as authority: navy/blue/amber, flat surfaces, restrained borders, 8-point spacing with existing 4 px subdivisions, 8/12/16 px corners. Fira Sans is bundled for Latin UI, Fira Code for identifiers/figures. Arabic uses the current system stack; Figma uses available Noto Sans Arabic as the representative fallback. Never fetch a runtime font from a third party.

At 1440 px the cockpit has findings plus contextual workflow; below 1200 px it becomes one column. At 768 px retain readable gutters, wrap context and actions. At 390 px the workflow starts collapsed, evidence uses a bounded dialog, and bottom navigation leaves safe-area clearance. At 320 px tables scroll in labelled regions while the page stays within the viewport. Keep the cockpit's essential controls sticky; long goals and large text need browser validation so they do not obscure focus.

Use 44 × 44 CSS px minimum controls, visible focus, semantic buttons/details/tabs and restrained polite announcements of actual changes. Compact legacy buttons are enlarged, and switches keep their visual track inside a larger touch area. Dialogs trap focus and restore it; long evidence opens at the dialog heading rather than jumping to a table. The navigation drawer traps Tab, makes the main area inert and restores its opener. The command palette supports Ctrl/⌘K. Status includes words and symbols. Respect both system and app reduced-motion choices; retain 140/220 ms token transitions otherwise.

Arabic mirrors application navigation, rows and alignment using document RTL and logical properties. Mixed filenames and paths use bdi or explicit direction. Digits remain 0–9. Stored report language is fixed at run creation and has its own lang/dir, independent of interface language.

## Future dashboard and native application proposals

Dashboards remain specification only. A4/A5 would add Summary, Trends, Drivers, Forecast & risk, and Quality pages; shared date/region filters; filter chips; accessible chart/table toggles; and drilldowns. They need server-computed aggregates, stable metric IDs/units, permitted dimensions, filter schema, freshness and provenance. Filter changes must cancel/ignore obsolete reads and be addressable; no client-side statistical engine or fabricated live badge.

Joins require the proposed A3 relationship/key and coverage contracts. Live connectors and schedules need ownership, credentials, execution and notification APIs. Advanced model cards need actual model/backtest/assumption fields. Workbook sheet selection needs an ingestion parameter and validation. None is silently enabled by a design.

The existing web app installs on supported Windows browsers, Android Chrome and iOS Safari via Add to Home Screen. This delivers an OS-launchable PWA with the same API and RTL UI. Signed Windows installers, Android AAB/APK, iOS archives, native file permissions, notifications and store submission are not delivered. A separate packaging decision should select wrappers or native clients, define identity/deep links/offline data policy, and run device testing with signing accounts.

## Incremental Codex implementation

1. Preserve backend contracts; add run snapshot store, event derivation and four-band plan with focused tests.
2. Complete sample → progress → finding/evidence → exact report → decision → returned publication path.
3. Connect inbox and assistant cards; add hash navigation and scoped draft recovery.
4. Retain existing ingestion/mapping; expose returned upload preview and sheets; add PWA installation guidance and generated decorative asset.
5. Run typecheck, component tests, production build, measured budget, Playwright and axe in both viewports/languages; inspect screenshot artifacts. Fix review findings in the main implementation.
6. Record human usability observations separately: manager comprehension within ten seconds, evidence within two interactions, keyboard approval, interrupted draft recovery and Arabic phone journey. Automated checks cannot establish human comprehension.

Performance targets remain approximately 100 KB gzipped JS, 10 KB gzipped CSS, 120 KB fonts; LCP <2.5 s, CLS <0.1 and INP <200 ms. CI measures the existing ADR 0028 first-load (100 KB), aggregate (160 KB) and largest deferred chunk (30 KB) budgets. Artwork is an additional 53,592-byte WebP fetched as decoration and cached with the shell; it is not JS, a chart, or analytical evidence. See the validation record for measured results and unresolved tradeoffs.
